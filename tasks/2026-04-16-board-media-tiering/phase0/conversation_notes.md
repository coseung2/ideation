## 영상 내용 정확 분석 (참고)

AWS S3가 느린 HDD 위에서 1PB/s를 달성하는 방법:

1. **병렬 분산 저장** — 파일을 잘게 쪼개 수천만 HDD에 분산 → 누적 처리량 확보
2. **Power of Two Choices** — 랜덤 2개 뽑아 사용률 낮은 쪽 선택. 종모양 분포를 평평하게 만듦
3. **Erasure Coding 5+4** — 원본 5조각 + 패리티 4조각, 아무 5조각으로 복구. 3중 복제(3x) 대비 **1.8x 오버헤드**. 느린 드라이브 응답 안 기다리고 버리는 게 가능해서 읽기 속도도 개선
4. **Heat Management** — 신규 데이터=핫, 오래된 데이터=콜드로 자연 냉각
5. **Shuffle Sharding** — 고객별 샤드 조합 무작위화로 장애 격리

영상이 단순화한 것: shuffle sharding, heat management, 3단계 병렬화(프론트엔드·드라이브·작업) 중 드라이브 병렬화만 다룸.

실제 수치: 400조 객체, 초당 1.5억 요청, 피크 1PB/s, 수천만 디스크, 단일 HDD 랜덤 I/O ≈ 32MB/s.

## 대안 탐색 결과

대안 5개 검토 후 정리:

| 안 | 내용 | 평가 |
|---|---|---|
| A | 썸네일 최적화만, 저장은 그대로 | 저장 비용 문제 해결 못 함 |
| B | S3 호환 Cold (R2/B2) | **채택 후보 1순위** — ToS 깨끗, 비용 낮음 |
| C | BYOS — 사용자 본인 드라이브 OAuth 연결 | 학생 OAuth 부담 과도 → 기각 |
| D | 원안 — 청크 분할 + 앱 공용 드라이브 | ToS·재조립·용량 다 걸림 → **기각** |
| E | 하이브리드 티어링 (핫=Aura/R2, 콜드=B2) | **채택 후보 2순위** — 학기 끝난 보드 자동 콜드화 |

**D안 기각 이유 (중요):**
- 청크 분할의 이득은 수천만 노드 규모에서만 성립. 노드 3~5개에선 병렬화 이득 0
- Google/OneDrive는 앱이 청크 스토리지/CDN처럼 쓰는 거 ToS 위반 소지
- 태블릿(갤탭 S6 Lite)에서 청크 재조립은 기존 렉 문제 악화
- Power of Two Choices는 Google/OneDrive에 즉시 사용률 조회 API가 없어 구현 불가
- **RAID도 "한 머신 안 여러 디스크"일 때 얘기지, 다른 클라우드 계정 묶는 건 아님**

## 문제 재정의

사용자 원래 동기는 **C(저장 한도/비용)**, 추가로 **B(렌더링 렉)** 도 인정.

| 병목 | 증상 | 해법 |
|---|---|---|
| A 업로드 시 | 태블릿에서 동영상 올릴 때 앱 멈춤 | 클라이언트 사이드 압축 |
| **B 보드 열 때** | 미디어 많아지면 스크롤·줌 렉 | **썸네일 온보드 + lazy load** |
| **C 저장 한도** | Supabase 요금제 상한 | **콜드 티어링 (R2/B2)** |

→ B와 C는 **한 아키텍처(2-Tier)로 동시 해결 가능**.

## 합의된 아키텍처 방향

```
┌─────────────────────────────────────────┐
│ HOT (Supabase, 현재 사용 중)            │
│   - 썸네일 (이미지: 400px WebP ~30KB)   │
│   - 비디오 포스터 + 10초 프리뷰 ~500KB  │
│   - 메타데이터 (원본 위치 포인터)       │
└─────────────────────────────────────────┘
           │ 클릭 시
           ▼
┌─────────────────────────────────────────┐
│ COLD (R2 or B2)                         │
│   - 원본 이미지/동영상 통짜              │
│   - 월 $5~15/TB (Supabase 대비 1/5~1/10)│
└─────────────────────────────────────────┘
```

### 구현 핵심 3가지
1. **업로드 시 썸네일 자동 생성** — 태블릿 클라이언트가 resize(browser-image-compression) → 썸네일만 Supabase 업로드, 원본은 R2/B2로 presigned URL 직접 전송
2. **클릭 시 스트리밍** — 비디오는 HLS 변환해 부분 스트리밍 (태블릿 이득)
3. **인덱스 DB** — Supabase에 `{thumb_url, original_url, bytes, uploaded_at}` 테이블

### 비용 비교 (대략)
- Supabase Pro: **$21/TB·월** (100GB 초과분)
- R2: **$15/TB·월**, 이그레스 무료
- B2: **$6/TB·월**, Cloudflare 경유 시 이그레스 무료

## 미정 / 다음 세션에서 결정할 것

1. **콜드 스토리지 공급자** — R2 vs B2 vs Tigris vs 기타 (phase1에서 비교)
2. **썸네일 생성 파이프라인** — 클라이언트 사이드 vs Supabase Edge Function vs 별도 서비스
3. **비디오 트랜스코딩** — HLS 변환 어디서? (태블릿·클라우드 함수·ffmpeg 서버)

5. **Free/Pro Tier 정책과 정합성** — 학생별/보드별 저장 한도 어떻게 정할지
6. **프라이버시·접근 제어** — R2/B2 원본 URL에 signed URL + 짧은 TTL? viewer 권한 검증?
7. **실패 모드** — 콜드 스토리지 장애 시 썸네일만 보이는 graceful degradation UX
