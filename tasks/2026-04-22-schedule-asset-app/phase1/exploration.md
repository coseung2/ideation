## 각 후보 장단점·적합 지점

### 1. 토스 자산/목표관리
- 장점:
  - 한국 마이데이터·오픈뱅킹 대응 최상, 금융앱 1위 수준의 데이터 커버리지(계좌·카드·보험·투자).
  - "목표 저축"·"세이프박스" 기능으로 자동이체·부분 잠금 저축을 제공. UX가 20~30대에 최적화.
- 단점:
  - 강제성이 "자동이체·격리" 수준에 머묾 — 일일 예산 초과 시 다음날 결제 차단 같은 능동 개입은 없음.
  - 토스 생태계 안에서만 작동(토스뱅크 계좌 등) — 외부 카드 결제 차단은 불가.
- 본 아이디어 적합 지점: 데이터 연동(조회)·세이프박스형 가상 잠금은 참고 모델로 삼고, 강제성 레이어는 별도로 얹어야 한다.

### 2. 뱅크샐러드
- 장점:
  - 국내 마이데이터 통합의 레퍼런스 — 계좌·카드·증권·보험·대출까지 조회 범위 최대.
  - 건강·자산 데이터 결합, 예산 대비 지출 분석·알림 견고.
- 단점:
  - '기록·분석·알림'만 제공. 예산 초과해도 '경고' 이상의 차단·페널티 없음 → 사용자 자기통제에 의존.
  - 마이데이터 사업자 지위·막대한 보안 투자 기반 — 1~2인 개발자가 흉내낼 수 없는 수준.
- 본 아이디어 적합 지점: "조회는 뱅크샐러드류의 마이데이터를 쓰지 않고, SMS/수동 기반으로 낮춘 뒤 강제성에 집중"이라는 포지셔닝의 역(逆)레퍼런스.

### 3. YNAB
- 장점:
  - "Give Every Dollar a Job" 제로베이스 예산 — 총지출 상한을 카테고리 단위로 사전 배분해 사후 초과를 구조적으로 어렵게 만듦.
  - 방법론·교육 콘텐츠가 강력(세계관 수준의 팬덤). 월/일 예산 개념이 명확.
- 단점:
  - 구독료가 비쌈($109/년). 한국 은행·카드 직연동 불가(수동 입력·CSV만).
  - 강제성은 심리·구조 레벨 — 초과해도 앱이 차단하지 않음, 사용자 판단에 의존.
- 본 아이디어 적합 지점: **제로베이스 예산 규칙**은 국내 앱에 비어있는 지점 — 차용 가능. 다만 차단 레이어를 얹어 차별화.

### 4. Qapital
- 장점:
  - "Rules" 엔진이 강력: "커피 살 때마다 $3 저축", "목표 초과 지출 날엔 저축액 2배" 같은 IFTTT식 룰 자동 실행.
  - 자체 FDIC 저축계좌를 발급해 이체·격리·인출 지연을 앱이 직접 제어.
- 단점:
  - 미국 SSN·미국 거주자만 가입 가능 — 한국 사용자 직접 도입 불가.
  - Freemium인데 핵심 기능은 유료, 사용자 이탈률 높음.
- 본 아이디어 적합 지점: **룰 기반 자동 이체·강제 저축** 메커니즘의 벤치마크. 국내에서는 자체 계좌가 없으니 토스/카카오뱅크 자동이체 API로 유사 구현 검토.

### 5. Beeminder
- 장점:
  - 목표 실패 시 사전 걸어둔 금액(pledge)을 실제로 과금 → "돈이 걸려 있어 안 지킬 수 없다" 수준의 최강 강제성.
  - 임의 데이터 소스 연결 가능(수기 입력, API, 통합 20+), 목표 그래프(yellow brick road) UX가 명확.
- 단점:
  - UX가 geek스러워 일반 20~30대 한국 사용자 진입장벽 큼(영문, 그래프 중심).
  - 지출 데이터 자동 수집은 약함 — 사용자가 수치를 꾸준히 입력해야 작동.
- 본 아이디어 적합 지점: **"실패 = 실제 금전 페널티"**라는 가장 강한 강제성 메커니즘의 레퍼런스. 국내에서는 기부 자동이체 또는 실패 시 적금 해지 불가 락업 형태로 변형 가능.

### 6. Freedom / One Sec (앱·사이트 차단)
- 장점:
  - 행동 차단의 OS 레벨 구현 레퍼런스 — iOS Screen Time API·Android Accessibility로 앱 실행을 지연·차단.
  - One Sec는 "앱 열기 전 10초 대기+심호흡" 같이 **행동 마찰**만 추가해도 사용 감소가 실증됨(연구 인용).
- 단점:
  - 금융 결제 자체는 막지 못함 — "쇼핑 앱 차단" 수준이 현실적 상한. 카드 결제는 OS·앱 레이어 밖.
  - iOS에서는 Apple의 스크린타임 권한·부모관리자 프로파일 필요 등 배포 제약.
- 본 아이디어 적합 지점: **쇼핑 앱·배달 앱을 예산 초과 다음날 차단/지연**이라는 형태로 "간접 차단"이 현실적 강제성 구현 경로임을 시사.

## 한국 계좌연동 기술 환경 (핵심 제약 정리)

- **마이데이터 API (금융위 본인신용정보관리업)**: 최소자본금 5억 원, 전산·보안 요건, 금융위 허가 필요. 1~2인 개발자 진입 **사실상 불가**. 조회 중심이며 이체·차단 기능 없음.
- **오픈뱅킹 API (금융결제원)**: 핀테크 사업자 등록 후 이용. 계좌 조회·이체 가능하나, 제3자가 사용자의 **카드 결제를 선차단**하는 기능은 제공하지 않음. 이체 API로 "목표 저축 자동이체" 정도는 구현 가능.
- **카드사 SMS 파싱**: Android는 `READ_SMS` 권한(민감 권한, Play Store 심사 엄격)으로 가능하나 Google은 2019년 이후 금융앱/백업앱 외 승인 거의 불허. iOS는 OS 차원에서 SMS 접근 불가.
- **실시간 지출 차단(카드 결제 거절)**: 카드 발급사·PG사와 직접 제휴 없이는 불가능. 기술이 아니라 제휴 문제. 현실적 대안:
  - "자동이체로 예산을 격리 계좌로 선이체" (격리 예산제)
  - "쇼핑·배달 앱 차단/지연" (OS 레벨)
  - "예산 초과 카드 사용 정지 = 사용자가 카드 앱에서 일시정지 요청을 앱이 유도·자동 호출" (제휴 없이는 수동)
  - "Beeminder식 페널티(실패 시 사전 동의 금액 자동이체)"
- 출처: 금융결제원 오픈뱅킹 안내, 금융위 마이데이터 고시, Google Play SMS/Call Log 정책 페이지 (본 섹션 세부 링크는 참조 링크 절 참고).

## 핵심 비교 축

- **강제성 강도**: 알림 < 룰 기반 자동저축 < 격리·잠금 < 페널티 < OS 앱 차단 (본 앱은 2~4 조합이 현실적)
- **국내 데이터 연동 실현 가능성**: 마이데이터(불가) > 오픈뱅킹 이체 API(가능) > SMS 파싱(조건부) > 수동 입력(항상 가능)
- **개발자 규모 적합성**: 1~2인이 커버 가능한 범위는 오픈뱅킹 이체 + SMS(안드로이드) + 수동 입력 + OS 차단 연계.
- **차별화 여지**: 국내 앱은 대부분 "기록·분석" 레이어. **일일 예산 초과 → 다음날 자동 조치(격리/차단/페널티)** 루프는 공백.

## 결론 (1차 권고 — 하이브리드)

**권고**: "**오픈뱅킹 이체 API + 사용자 자발 SMS 파싱(Android) / 수동 보완(iOS)** + **룰 기반 예산 격리(Qapital 스타일) + 실패 시 페널티(Beeminder 스타일) + 쇼핑앱 OS 차단(Freedom 스타일)**의 3층 강제성 구조, 플랫폼은 **Android 우선 + iOS는 차단 축소판**"으로 시작한다.

근거: 한국 규제상 1~2인 개발자가 "실시간 카드 결제 차단"은 불가능하므로, 강제성을 (1) 예산 초과 전 **사전 격리**(오픈뱅킹 자동이체로 저축 계좌에 먼저 옮김), (2) 초과 시 **사후 페널티**(사용자 사전 동의한 금액을 지정 계좌·기부처로 자동 이체), (3) 행동 마찰(**쇼핑·배달 앱 OS 레벨 차단·지연**)의 3층으로 구성해야 한다. 데이터 수집은 마이데이터가 막혀 있으니 Android는 SMS 파싱 + 수동 보완, iOS는 수동 입력 + 카드사 앱 스크린타임 연계로 낮춰 간다. 일정관리는 예산 이벤트(월급일·카드 결제일·목표 마감일)를 캘린더로 시각화해 "일정+강제성" 결합의 고유 가치를 만든다.
